# 数据源能力改造（独立议题）

> 本文档独立讨论数据源管理与配置化能力，不纳入 `docs/redesign-v3.md` 的当前主线范围。

---

## 1. 为什么单独拆出

数据源能力改造是合理方向，但它更接近**平台能力建设**，而不是本轮 authoring redesign 的核心主线。

当前主文档聚焦的是：

- AI 主创作链路可靠性
- 创作体验产品化
- 相关稳定性支撑

而数据源议题关注的是：

- 数据源注册与管理
- 连接测试与权限边界
- 多数据源扩展方式
- 后端 schema / context 的动态加载能力

它的重要性不低，但叙事重心不同，因此拆成独立文档更清晰。

---

## 2. 当前问题

基于当前代码，数据源能力的主要限制包括：

- 数据源实现基本写死在单一默认 datasource 上
- 产品内没有正式的数据源管理入口
- 新增数据源需要改代码，而不是走产品配置
- Agent 虽然有 datasource 能力接口，但底层扩展性不足

一句话概括：

> **当前数据源更像工程内置配置，而不是产品能力。**

---

## 3. 后续目标

如果后续单独启动这条线，目标建议聚焦为：

### 目标一：让数据源成为产品内可管理对象

用户或运营侧应能在产品内看到、创建、编辑、测试数据源，而不是只能改代码。

### 目标二：让 Agent 面向动态数据源工作

Agent 获取 datasources、读取 schema、选择 datasource 时，应建立在可扩展的数据源定义之上，而不是默认只有一个内置选项。

### 目标三：为多数据源扩展留出边界

后续即使暂时只支持 PostgreSQL，也应该把能力边界设计清楚：

- 数据源元信息存放在哪里
- 连接测试如何进行
- 可见表/字段白名单如何表达
- Agent 能拿到什么粒度的 schema 上下文

---

## 4. 可考虑的改造范围

### 4.1 管理页增加数据源入口

方向上可以考虑在管理页增加独立的数据源入口，用于承载：

- 数据源列表
- 连接状态
- 测试连接
- 创建 / 编辑 / 删除

### 4.2 后端配置化

方向上可以考虑：

- 将 datasource 定义移出硬编码实现
- 支持动态列出 datasource
- 支持按 datasource 加载 schema/context
- 为后续多数据源并存留出能力边界

### 4.3 权限与风险边界

数据源能力不是纯 UI 功能，它天然带有风险边界问题，例如：

- 连接信息如何保存
- 哪些表对 agent 可见
- 连接失败如何反馈
- 是否允许直接删除数据源

因此即使未来启动，也不建议只当成简单“列表页”来做。

---

## 5. 为什么现在不做

目前更优先的问题仍然是：

- AI 创作链路还不够连续
- Authoring 页产品化程度还不够
- 一些交互与稳定性问题会直接影响主体验

如果此时把数据源一起纳入主 redesign，会让当前文档变得过宽，任务拆分也会失焦。

因此更合理的策略是：

1. 先完成 authoring redesign 主线
2. 再单独启动 datasource 能力设计
3. 以独立议题推进其后端、UI、权限与扩展性问题

---

## 6. 启动条件建议

当以下条件基本满足时，可以考虑正式启动数据源议题：

- AI 主创作链路已经足够稳定
- 创作页的主要产品化工作已经完成
- 团队能接受启动一个更偏平台能力的子项目

---

## 7. 一句话总结

数据源能力改造是**后续值得单独推进的独立方向**，但不应该继续占据当前主 redesign 文档的核心叙事。
